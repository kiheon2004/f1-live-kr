# LiveTimingKR 전략 게임 — 엔진 설계 (v0.48)

이 문서는 게임 엔진의 계약(구조·단위·상태·시간 진행·데이터 경계·검증 기준)이다. 구현은 이 문서를 따른다. 바꿀 때는
이 문서를 먼저 고친다. 사용자 요구: `~/projects/f1kr-work/v048/request.md`(이하 "요청 §n").

## 0. 원칙

1. **라이브타이밍과 분리.** 게임 코드는 `src/game/`(엔진, 순수)와 `src/renderer/game/`(화면·3D 어댑터)에만 둔다.
   라이브타이밍 모듈(`replay.js`, `smooth.js`, `traffic.js`, `app.js`의 replay/live 경로, `map3d.js`의 기존 경로)은 게임
   상태를 읽거나 쓰지 않는다. 게임은 라이브 캐시(`~/Library/Application Support/f1-live-kr/cache`)를 **읽기만** 한다
   (시나리오를 만들 때, 오프라인 도구에서). 게임 자료는 `userData/game/`(시나리오·저장)에만 쓴다.
2. **엔진은 순수.** `src/game/engine/**`는 DOM, Three.js, `window`, `performance.now()`, `Date.now()`, `Math.random()`을
   쓰지 않는다. Node에서 `import`해 한 경기를 끝까지 돌릴 수 있다.
3. **결정성.** 같은 시나리오 + 규칙 + 성능 자료 + 시드 + 명령 로그 → 같은 결과. 배속·FPS·3D·카메라와 무관하다.
4. **인과.** 결과는 상태에서 나온다. 랩타임 보정표, 순위 확률표, "언더컷 보너스" 같은 결과 직접 조작은 없다.
5. **출처 표시.** 모든 계수는 `src/game/data/params/*.js`에 단위·의미·출처·범위·추정 여부와 함께 있다(`PARAM` 표).
   공개 자료로 정할 수 없는 값은 `est: true`(게임용 추정)로 표시하고 화면에도 그렇게 보인다.
6. **정답 금지.** 시나리오에 그 경기의 실제 결과(최종 순위, 실제 피트 랩, 실제 SC 시각)를 엔진 입력으로 넣지 않는다.
   실제 출발 순위·참가자·랩 수·날씨 기록·서킷 형상은 입력이 될 수 있다(경기 전에 알 수 있는 사실, 날씨는 아래 §9).

### 1.1 엔진 상태 형태 (계약)

경기 상태 `race.state`는 JSON으로 저장 가능한 평범한 객체다(파생 캐시 — 트랙 배열, 포락선 — 는 `race.cache`에 두고
복원 때 다시 만든다).

```js
state = { v: STATE_VERSION, t /* ms */, step, seed, scenarioId, rulesSeason, totalLaps, finished,
  cars: [car], order: [num…] /* 현재 순위 */, control: {...control.js}, surface: {...weather.js},
  boxes: {...pit.js}, commands: {...commands.js}, ai: { [teamKey]: {...} }, log: [event], results: null }
car = { num, teamKey, team, tla, driverId, grid /* 출발 슬롯 1.. 또는 null */, pitStart,
  status: "grid"|"run"|"pit"|"fin"|"dnf", out: null | { cause, t, lap },
  where: "lap"|"pit", s, d, v, aLong, aLat, steer, wheelDist,
  lap /* 완료 랩 */, dist /* 출발선 기준 경주 거리 m(그리드는 음수) */, lapT0, laps: [{ n, t, sectors, compound, pit, flag }],
  tyre: {...tyre.js}, energy: {...energy.js}, driver: {...driver.js}, mode: { pace, energy },
  plan: { stints: [{ compound, toLap }] }, pit: {...pit.js}, traffic: {...traffic.js},
  pen: { pendingS /* 피트에서 서비스할 시간 */, finalS /* 결과에 더할 시간 */, serve: [{ kind, given }] },
  acct: { traffic, pit, tyre, energy, penalty, other } /* 초, §12 */ }
```
순위: `status` 완주/진행 차량은 `dist` 내림차순(같은 랩 내 위치), 피트 차량은 `pit.pitToLap(u)`로 환산. 리타이어는 뒤.

## 2. 시간

- **세 시계.** 벽시계(사용자 시간, 화면 쪽에서만 `performance.now()`), 시뮬레이션 시각 `t`(정수 ms, 엔진 상태),
  렌더 시각(화면이 그리는 시뮬레이션 시각 = 마지막 두 스냅샷 사이 보간 지점, 항상 `t` 이하).
- **고정 간격 `DT = 50 ms`.** 근거: 최고 속도 ~95 m/s에서 한 걸음 4.75 m(차 길이 5.6 m 미만) → 추종·나란히 판정이
  한 걸음에 차를 건너뛰지 않음. 22대 × 랩 90분 ≈ 10.8만 걸음 × 22대 = 240만 차량-걸음. 차량-걸음 비용 목표
  ≤ 5 µs → 헤드리스 한 경기 ≤ 15 s, 30배속 실시간 = 초당 600걸음 × 22대 ≈ 13만 차량-걸음/s(여유 큼).
  정확도 확인: `DT = 25 ms`와 단독 랩타임 차 < 0.02 s, 같은 시드 경기 순위 변화 원인 분석(`test/game/dt.test.js`).
- **실행기.** `advance(targetT, budgetMs)`: `t + DT ≤ targetT`인 동안 한 걸음씩. 예산을 넘으면 멈추고 "따라가지 못함"을
  보고(화면은 실제 달성 배속을 표시, 요청 §4). 배속은 목표 시각을 빨리 움직일 뿐 `DT`는 그대로.
- **일시정지.** 걸음을 실행하지 않음 → 상태 불변(테스트). 명령은 일시정지 중에도 접수되며 다음 걸음의 시각으로 고정.
- **자동 감속(선택).** 중요 사건(SC, 비 시작, 피트 윈도, 팀 동료 충돌 위험)을 엔진이 사건으로 알리고, 화면 실행기가
  배속을 낮춘다. 엔진 결과에는 영향 없음.

## 3. 난수

- `sfc32`(32비트 상태 4개). 마스터 시드 → 스트림 이름(`"driver:16"`, `"pit:ferrari"`, `"incident"`, `"weather"`,
  `"ai:mclaren"`) 해시로 독립 스트림 생성. 한 하위 모델이 난수를 더 쓰거나 덜 써도 다른 모델의 난수열이 바뀌지 않는다.
- 저장 시 모든 스트림 상태를 저장(시드 재초기화 금지).
- 걸음마다 독립 난수를 속도에 더하지 않는다(요청 §6). 드라이버 변동은 AR(1) 과정(시간 상수 수 초~수십 초)으로,
  걸음마다 `x ← ρx + σ√(1−ρ²)·N(0,1)`, `ρ = exp(−DT/τ)`.

## 4. 주행용 서킷 모델 (track.js, 시나리오의 `track`)

시각 지형과 별개다. 시나리오 생성기가 그 경기의 위치 자료(F1 Position x,y,z, 1/10 m)로 만든다.

- **표본**: 랩 라인을 따라 `ds = 2 m` 등간격. 각 표본: `s`(m, 출발선 0), `x, y, z`(m, F1 좌표 → m), `hdg`(rad),
  `kappa`(1/m, 부호: 왼쪽 +, 평활), `grade`(무차원 dz/ds, 평활), `wL, wR`(랩 라인에서 왼쪽/오른쪽 주행 가능 폭, m),
  `line`(기본 레이싱라인의 횡오프셋 m), `zone` 비트(제동, DRS/직선 모드, 피트 진입/출구, 섹터, 터널 덮임 등).
- **곡률**: 위치 오차(1–2 m)를 고려해 σ ≈ 6–10 m 가우시안 평활 후 3점 원 곡률. 실제 텔레메트리 최저 속도와 비교 검증.
- **고저**: 위치 자료 z를 ±20 m 평균(라이브 buildWorld와 같은 원리). **다른 높이의 도로를 연결하지 않음**: 랩 라인은
  한 차량의 실제 주행 순서이므로 교차로(스즈카)에서도 순서가 보존된다(평면 근접으로 잇지 않음).
- **폭**: 공개 데이터에 노면 폭 측정이 없음 → 서킷 기본값(라이브 CIRCUIT_STYLE.w와 같은 출처, 추정) + 피트 직선/시가지
  보정. `est: true`. (지도 기반 폭은 이후 과제.)
- **피트 경로**: 위치 자료의 피트레인 주행(InPit 구간)으로 피트 경로 표본(별도 배열), 진입 분기 `sIn`, 합류 `sOut`,
  제한 속도 구간 시작/끝(경로 거리), 팀 박스 위치(경로 거리, `pitorder.js` 실측 순서 재사용), 레인 제한 속도
  (규칙/서킷별, 출처 표시).
- **구간 자료**: DRS 구간(2011–2025, 실제 텔레메트리 DRS 열림 위치에서 추정 + 공식 자료 있으면 우선),
  2026 직선 모드 구간(라이브 aero.js 공식 목록 재사용 + 추정), 섹터 경계, SC 라인.
- **추월 공간**: 표본별 `pass` 지표 = (폭 − 2 × 차폭 − 여유) ≥ 0 이고, 앞선 직선 길이와 뒤 제동 구간이 있는 곳.
  추월 판단은 이 지표와 실제 속도 차로 한다(§8).

## 5. 차량·속도 (profile.js, car.js)

단위 SI. 점질량 준정적 모델(공개 자료로 식별 가능한 수준).

- **그립 한계**: 횡가속 한계 `a_lat(v) = μ_eff · (g + ClA·ρ·v²/(2m))` (ClA: 다운포스 면적 계수 m², ρ 공기밀도
  kg/m³, m 질량 kg). 코너 속도 `v_c(s) = sqrt(a_lat(v_c)/|κ|)` (고정점 반복). `μ_eff = μ_tyre(상태) × μ_track(수분·
  고무) × u_driver(활용도 ≤ 1) × f_dirty(추종)`.
- **종방향**: `m·a = F_drive − ½ρCdA·v² − C_rr·m·g − m·g·grade`, `F_drive = min(P(v,에너지)/v, 견인 한계)`;
  제동 `a_brake ≤ min(μ_eff·(g + 다운포스/m)·k_brake, a_brake_max)`. 횡가속을 쓰는 중에는 마찰원으로 종방향 한계 축소.
- **포락선**: 차량마다 현재 계수로 뒤에서 앞으로 제동 포락선 `v_b(s)` + 코너 상한 `v_c(s)` 계산(표본 2 m, 한 번에
  ~O(n)). 계수가 기준 이상 바뀌면(타이어 그립 0.3 %, 질량 5 kg 등) 또는 2 s마다 다시 계산. 걸음마다 가속은 동역학으로
  적분하고 속도는 `min(v_b, v_c)`로 제한(가속 쪽 포락선을 따로 두지 않음 → 슬립스트림·에너지가 자연스럽게 반영됨).
- **효과 중복 금지**: 타이어·연료·에너지·추종 효과는 위 식의 해당 항에만 들어간다. 랩타임에 초를 더하는 항은 없다
  (예외: 규칙 페널티 시간은 분류에 더한다).
- **팀 차량 계수**(`params/cars-<season>.js`): `m_min`, `P_ice`, `P_ers`, `CdA`, `ClA`, `μ_mech`, `a_brake_max`,
  `k_low/k_mid/k_high`(저·중·고속 코너 보정, 보정 자료가 요구할 때만 ≠ 1), `C_tyre_heat`(타이어 부하 계수),
  `reliab`(고장 위험 기준). 보정: 보정 경기 집합의 실제 텔레메트리(최고 속도·코너 최저 속도·가속 구간)와 랩타임에
  맞춤(`tools/calibrate.mjs`), 검증 경기 집합에서 오차 보고. 같은 팀이 서킷마다 다른 차이를 보이는 것은 계수(저항 대
  다운포스 대 출력)와 서킷(직선 비율·코너 속도 분포)의 상호작용으로 생긴다.

## 6. 드라이버 (driver.js, `params/drivers-<season>.js`, 전부 게임용 추정 `est: true`)

`pace`(평균 활용도, 0.985–1.000), `consistency`(AR(1) σ), `tyreMgmt`(타이어 발열 계수 배율), `racecraft`(추월·방어
판단과 접촉 위험), `wet`(우천 활용도 배율), `compliance`(팀 지시 수행 성향). 차량 계수와 겹치지 않게: 차량은 한계(μ, ClA…),
드라이버는 그 한계를 쓰는 정도.

## 7. 타이어 (tyre.js) — 엔진 핵심

상태(차량별): `compound`, `age`(랩·km), `wear`(0–1, 비가역), `Ts`(표면 °C), `Tc`(내부 °C), `set`(새/중고),
`flat`(플랫스폿 여부, 2단계). 매 걸음:
- 입력 에너지 `Q = C_tyre_heat · tyreMgmt · (|a_lat| + |a_long|) · v · pace모드계수`(J/s 상대 단위, 보정됨).
- 온도: `dTs = (Q·kq − hs(v)·(Ts − Tc) − ha(v)·(Ts − Tair_track))·DT`, `dTc = (hc·(Ts − Tc) − hl·(Tc − Tamb))·DT`.
- 그립: `μ = μ_peak(compound, wet) · W(Ts, Tc; 창) · Gw(wear) · Gr(rubber, 노면)`. `W`는 창 밖에서 감소(가역).
- 마모: `dwear = k_wear(compound, 노면 마모도) · Q · H(Ts)·DT`. `H`는 과열 시 증가(비가역 손실 증가) — 과열의 즉시 손실은
  `W`(가역), 누적 손실은 `wear`(비가역)로 분리.
- 범위: `0 ≤ wear ≤ 1`, 온도는 물리 범위로 제한, `μ`는 유한·양수(테스트).
- 젖은 노면: 컴파운드별 `μ_peak(wet)` 곡선(드라이 슬릭은 수분이 늘면 급감, 인터는 중간, 웨트는 깊은 물에서 유리),
  마른 노면의 인터/웨트는 과열·마모 증가.
- 그레이닝·블리스터링은 기본 모델 검증 뒤(원인·검증 방법을 설명할 수 있을 때만).

## 8. 교통·추월 (traffic.js)

- 차량: 길이(규정에 길이 조항 없음 → 2024–25 5.63 m, 2026 5.43 m, 추정), 폭 = 규칙 자료 `dimensions.maxHalfWidthMm × 2`
  (2.0 m / 1.9 m), 위치 `(s, d)`(d: 기준선에서의 횡오프셋, +왼쪽). 차량은 레이싱라인 기준 오프셋 `e = d − line(s)`를 가진다
  (자유 주행 e = 0 → 라인을 정확히 따름). 계수: `data/params/traffic.js`.
- **상태**(car.traffic.state): `free` → `follow`(앞차 1.5 s 안) → `prepare`(1 s 안, 접근 중이거나 DRS/Overtake 자격, 다음
  코너가 추월 장소 – 견인 속에 머물며 에너지 사용, 제동점 전 예상 이득 ≥ 필요 거리면 옆으로 빠짐) → `alongside`(차체 겹침)
  → 코너 턴인에서 반 차 길이 넘게 앞선 차가 코너를 가짐, 나란하면 안쪽 차 → `complete`(상대가 양보) / `abort`(스스로 양보);
  앞차: `defend`(제동점 전 한 번 안쪽으로 – 그 코너를 안쪽 절반으로 도는 것이 비용), `yield`(청기 – 규칙 자료 간격, 팀 지시
  swap, 코너를 잃음, 공격하지 않는 나란히 주행에서 뒤차), `merge`(피트 출구 쪽 블렌드 거리), `pitIn`(진입 쪽으로 이동), `pit`.
  역할(role/with)이 상대 차를 가리킨다. 모든 판단은 걸음 시작의 필드만 읽는다(배열 순서 무관 – 테스트).
- **공간 규칙**: 같은 차선(|Δd| < 폭 + 여유)의 앞차 뒤에서는 Gipps(1981) 안전 추종 속도 AND 접근 속도 규칙(접근 속도 ≤
  간격/T_c – 코너 한계에서는 마찰 타원 때문에 제동 여력이 거의 없음). 횡이동은 ≤ vLat, 옆 차(|Δs| < 길이 + 여유)와 겹치지
  않게, 앞/뒤 차의 차선으로는 뒤차가 안전할 때만(끼어들기로 남을 밀어내지 않음), 도로 폭 안에서만. 그래도 피할 수 없는
  추돌(코너 한계에서 앞차가 느려짐)은 **접촉 사건**: 비탄성 해결(뒤차가 한 차 길이 뒤, 앞차 속도) + 로그 + `race.hooks.incidents
  .onContact` – 상태에서 차체는 절대 겹치지 않는다(테스트가 매 걸음 확인). 위험 후보(턴인에서 나란히, 압박)도 같은 훅으로.
- **코너 비용**: 나란히/라인 밖에서 코너를 도는 차는 도로 일부만 쓴다 → 유효 반경 `R = R_lane + (R_line − R_lane)·share`
  (share = (차선 폭 − 차 폭)/(도로 폭 − 차 폭), R_lane = 차선 중앙의 기준선 평행 경로), 그리고 경로 길이 `(1 − κ·d)`(안쪽이 짧음,
  `pathFactor`). 코너 속도는 차량 자신의 v_c에 닫힌 식 비율을 곱하고 같은 마찰 타원으로 제동 – 300 m 앞보기 창(car.js `capArr`).
- **웨이크**: 더티에어 = 추종 차의 **ClA** 감소(원인이 다운포스 손실이므로 μ가 아니라 ClA: v²에 비례해 중·고속 코너에서
  크고 헤어핀에서 작음 – 설계 초안의 "μ_eff × f_dirty"를 바꿈), 거리 멱법칙(10 m 22 %, 20 m 10 %, F1.com 2022 목표를 하한으로),
  2 s 밖은 없음, 횡으로 감쇠; 슬립스트림 = **CdA** 감소(10 m 15 %, 1/x, 1 s 밖 없음, 순수 추정). 둘 다 같은 창/걸음 계수로만
  들어가고 랩타임 항은 없다.
- **DRS / Active Aero / Overtake – 별개**: DRS(≤2025)는 감지점에서 앞차와 1 s 안(규칙 자료) → 그 구간에서 열림, 제동 직전 닫힘
  (cdaMul/claMul: cars-base drs). 2026 Straight Mode는 구간 안 모든 차(간격 조건 없음, 저그립은 앞날개만), 제동 직전 닫힘.
  2026 Overtake는 감지선(추정 위치)에서 1 s 안 → 활성선부터 한 랩 동안 energy.js `ersCap(…, otEligible)` + 랩 회수 +0.5 MJ.
  허용 여부는 `race.hooks.control`(control.js: drsAllowed / activeAeroAllowed / overtakeModeAllowed / mayOvertake)가 있으면 그것,
  없으면 시즌 규칙의 단순 조건.
- **에너지 장면**: 공격(prepare/alongside)·방어 중에는 팀 모드의 예산·SOC 하한 안에서 배치 비율을 올린다(harvest는 제외);
  2026 Overtake 활성 + 공격 장면 → "overtake" 모드.
- **교통 시간 계정**: 교통 영향이 시작되면 그 차의 "유령"(같은 차·포락선·출력·질량·비교통 상한, 교통 없음)을 같은 자리·속도에서
  출발시켜 매 걸음 적분; 손실 = 같은 거리에서의 시간 차(10 m마다 유령 통과 시각). 마지막 영향 5 s 뒤, 피트 진입, 매 랩 선에서
  끝냄(새 유령). 음수 = 견인/DRS 이득. 근사: 교통이 없었을 때의 타이어·배터리 변화는 모름, 랩마다 다시 시작할 때 그 순간의
  속도 손실은 세지 않음. 단독 주행과의 비교 테스트.
- 순위는 실제 이동 결과(누적 거리)로만 바뀐다. 추월은 차체 한 길이 앞섰을 때 기록(장소·원인).

## 9. 날씨·노면 (weather.js)

- **진실 시나리오**(엔진 내부): 시간별 강우 강도(mm/h), 기온·노면 온도, 바람. 모드: (a) 실제 기록 기반 — F1
  WeatherData는 강우 유무(0/1)만 있으므로 강도는 추정(`est`), 기록이 빈 구간은 보간 + 추정 표시; (b) 생성 — 마르코프
  강우 과정(시드).
- **예보**(팀이 아는 것): 진실에 오차·지연이 있는 확률 예보(예: 15분 단위 강우 확률), 시간이 갈수록 가까운 미래가
  정확해짐. AI와 사용자 모두 같은 예보만 본다(요청 §11, §13).
- **노면 수분**: 구간(예: 100–200 m)별 수막 깊이 `h`(mm): `dh = (R·cover − drain(h) − dry(h, Ttrack, 바람) − traffic(h, 통과
  차량 수, 레이싱라인))·dt`. 터널·지붕은 `cover = 0`(라이브 weather.js의 덮임 개념과 같은 원리). 비가 그쳐도 즉시 마르지
  않음. 레이싱라인이 먼저 마름(라인 위와 밖의 `h` 분리, 2단계).
- **그립 연결**: `μ_track(h, 고무)`와 타이어 컴파운드 적합성. 스프레이·시정: 앞차 간격과 `h`로 추종 차량의 활용도 감소.
- **화면 일치**: 3D 날씨는 게임 모드에서 엔진의 진실 상태(현재)만 받는다(§13). 화면 비 = 엔진 비.

## 10. 규칙·레이스 컨트롤 (rules.js, control.js, data/rules/<season>.js)

시즌별 자료(조항·출처·확인일): 점수, 완주 분류(90 %), 타이어(건조 시 두 종류 의무 등), 피트레인 속도, 페널티 종류
(5/10 s, 드라이브스루, 스톱앤고), SC/VSC 절차(추월 금지, 델타, SC 뒤 정렬, 랩 다운 차량 언랩, 재개), 레드플래그(피트레인
대기, 자유 타이어 교체), 시간 제한, DRS 사용 조건(2011–2025), 2026 Active Aero·Overtake Mode·에너지 한도.
구현하지 않은 규칙은 `implemented: false`로 자료에 남기고 화면에 "미구현"으로 보인다.
SC/VSC는 속도 비율이 아니라: VSC는 차량별 델타 시간(최소 구간 시간) 준수, SC는 SC 차량이 트랙 위 개체로 달리며
선두가 따라붙고 간격이 줄어듦(추월 금지, 피트는 열림/닫힘 규칙 따라), 재개 절차.

### 10.1 엔진 연결 (v0.48 리드 연결, engine.js)
- 한 단계: 명령 → 날씨 → 교통 결정(trafficPre) → **단계 시작 상태로** 차량별 `control.caps`(속도 상한·그립 사용 계수·출발
  런치)와 피트 입력(`control.pitCtx` ⊕ `rules.pitCtx`: noBox/holdU/penaltyS/noWork) → 이동 → trafficPost →
  `controlStep`(이번 이동의 선·구간·SC선 통과, SC 차량, 깃발, 출발·종료) → `rules.stewardsStep` → 사건(`driverError`,
  `mechanical`; 접촉은 traffic이 `race.hooks.incidents.contact`로) → 순위 → 종료 시 `rules.classify` → AI.
- 출발: 등화 1 s 간격 5개, 소등은 시드 지연, 드라이버별 반응·런치 품질(`start:<num>` 스트림). 피트레인 출발 차량은
  레인 끝에서 대기하다 그리드 차량이 모두 출구를 지나면 합류.
- 운전 실수 입력 u: 단계 끝에 차가 포락선 위(제한 속도의 97 % 이상, 상한에 걸린 경우 제외)에 있을 때만
  `errU0 + errGain × (포락선 μ ÷ 지금 μ − 드라이버 기본 pace)`. 손상(`car.dmg`)은 ClA·출력으로 차량 모델에 들어간다.
- 차고 리타이어 차량은 `where: "garage"`로 레인에서 빠진다. 체커 뒤 3 s가 지난 차는 화면에서 사라진다(쿨다운 랩 미구현).
- 결과: `results()`는 rules.classify 행 + `gap`(초)·`lapsDown`·`stops`·`stints`·`acct {traffic≈, pit≈, pitQueue≈, penalty}`.
- 저장: `state.control`, `state.incidents`, `car.inc/dmg/dmgKey/fin`이 상태에 포함, 복원 시 `refreshControlCache`.

### 10.2 명령과 화면 시각 (v0.49)
- 명령: 받을 때(`commands.shape` + `engine.validateOrder`: 차량·팀 존재, 소속, 모드, 이 이벤트의 컴파운드, 스틴트 끝 랩
  순서와 결승 도달)와 적용할 때(상태: 리타이어·완주·경기 종료) 두 번 검사, 적용 중 예외는 거절로 기록. 명령을 내린 쪽은
  호출 경로가 정한다: `command()` = 플레이어, AI는 `commandAs(race, cmd, "ai:<team>")`. `commandStatus(race, id)` =
  queued / applied / refused(+이유, 단계).
- 사용 가능 컴파운드: `compounds.js availableCompounds(scenario)` 하나를 엔진·AI·화면이 공유(지정 자료 + 인터·웨트,
  없으면 추정 표시; 실제 경기에서 쓰인 목록은 쓰지 않음; 세트 재고 없음).
- 이산 상태(본선/피트/차고, 상태, 피트 단계, 장착 타이어)의 변화는 차량별로 그 sim 시각과 함께 `car.trans`에 남고(최근
  12개·60 s), 스냅샷 `trans`로 화면에 간다. adapter3d `frameCars()`는 이전 스냅샷 상태에서 시작해 렌더 시각이 지난
  변화만 순서대로 적용한다(미리 보이지 않음). 정비 시간·느린 바퀴는 작업이 끝날 때 로그에 남는다.
- 스냅샷 추가: `energy.deployKw`(실제 ERS 배치 출력), `mode {pace, energy}`, `pit` 단계 시각(일어난 것만), `err.wheel`.

### 10.3 조작 권한·목표 보조·타이어 세트·화면 시각 계약 (v0.50)
- 엔진 버전 `0.50.0-engine.1`. 경기 움직임이 바뀌는 것은 타이어 세트 하나다: 세트가 부족한 계획·피트 요청은 거절되고
  AI는 세트 안에서만 계획한다. 가정 배정 안에서 끝나는 경기는 0.49와 같다(같은 단계·명령·추첨: 영국 2025 시드 1의 30분
  지문 동일). 하스가 미디엄 3스틴트를 계획하던 헝가리 2025 시드 1은 바뀐다(가정 배정 미디엄 2세트). 2026 MGU-K 속도
  상한 둘째 구간(340–345 km/h) 추가로 2026 경기의 최고속 직선 구간도 바뀐다. 그 밖의 추가 상태는 경기 움직임이 읽지 않는다.
- 조작 권한 `state.own[num] = { pace, energy, plan: "ai"|"player"|"goal", by }`(플레이어 차량만). **적용된** 플레이어
  명령만 그 종류를 플레이어로 옮긴다(거절된 명령은 아무것도 바꾸지 않음 – v0.49 점검 3-1). `delegate`가 종류를 AI에
  돌려주고(로그는 지우지 않음), AI는 `own[kind] !== "ai"`이거나 같은 종류의 플레이어 명령이 대기 중이면 손대지 않는다
  (적용 거절로 큐가 비면 바로 다시 판단). 저장·복원에 포함, v0.50 이전 저장은 **적용된** 명령으로만 복원(migrate).
- 목표 보조(assist.js): `goal` 명령 → keep / attack / defend / tyre / save. 행위자 `goal:<team>`의 pace·energy 명령만
  만든다(검증 동일, 랩타임 보너스·강제 추월 없음). 2 s마다 판단, 같은 종류 명령은 8 s 간격 이상, 히스테리시스 띠,
  SC/VSC/적색기·피트레인에서는 대기, 수동 pace/energy 명령이 오면 목표 종료, 상태·이유 코드는 스냅샷 `goal`. 연료 목표는
  없다(연료 소모가 페이스 모드에 거의 의존하지 않는 모델 – 리프트 앤 코스트 없음).
- 타이어 세트(inventory.js): 차량별 세트 목록(가정 배정: 드라이 컴파운드별 새 2 + 예선 소프트 중고 1, 인터 4, 웨트 3 –
  실제 주말 재고 자료 없음, `est`). 피트 요청이 세트를 예약 → 작업 끝에 장착(이전 세트는 사용 흔적과 함께 반납) → 취소·
  작업 없는 정지는 예약 해제. 계획은 남은 스틴트마다 세트가 있어야 받는다. 스냅샷 `sets`는 플레이어 차량만.
- 계측선 간격: 차량마다 랩당 40개 지점의 통과 시각(최근 2랩)을 남기고, 간격 = 같은 지점의 통과 시각 차(`gap.how
  "line"`), 자료가 없으면 null(0이 아님). `last`/`best` 랩, `tyre.win/Tw/life`, 랩 기록에 교통 손실·에너지 모드·온도.
- 화면 시각 계약(renderer/game/present.js): 연속값은 보간(랩↔피트, 타이어 교체를 가로지르지 않음), 이산값(위치·상태·
  피트 단계·장착 세트·랩·순위·모드, 레이스 전체의 깃발·단계·선두 랩)은 이전 스냅샷 + 기록된 변화(`trans`/`rtrans`,
  최근 48개·120 s, 잘린 구간은 `transCut`까지 이전 상태), 추정값은 이전 스냅샷. 3D·순위표·카드·카메라 대상·날씨·크루가
  같은 그림을 쓴다. 명령 표시는 렌더 시각이 적용 시각에 닿기 전까지 "대기".
- `strategy.pitOptions(race, num)`: 지금 / +1 / +2 / 계획 유지 – 손실 범위, 지금 간격 기준 복귀 순위 범위·앞뒤 차·교통,
  예열, 팀 동료 대기, 규정, 세트, 늦출 때 이전 타이어 비용(팀 모델 추정). 상대 계획·연료·마모는 읽지 않는다.
- `analysis(race)`: 계획 변경 이력(누가·언제), 실제 스틴트, 명령, AI 판단, 피트 손실 구성, 랩별 교통 손실, 깃발 변화 –
  반사실("다른 전략이면") 계산 없음.

## 11. 피트 (pit.js)

단계: `call`(명령 접수) → `committed`(진입 결정 지점 `sIn − D_commit` 통과: 이후 취소 불가) → `entry`(감속, 분기)
→ `lane`(제한 속도) → `approach`(박스 감속) → `stop`(정지) → `work`(작업: 잭·휠건·교체, 엔진이 시간 결정) →
`release`(출발, 안전 출발 판단) → `laneOut` → `exit`(합류, 교통 상태로). 같은 팀 두 번째 차가 박스에 오면 `queue`.
- 피트 박스는 팀당 1개(작업 지점) — 차고 문 개수와 무관(요청 §10).
- 작업 시간: 휠별 시간 분포(정상), 실수 사건(휠너트 지연 등)은 원인·확률·시드(`pit:<team>` 스트림)로.
- 새 타이어 상태는 `work`가 끝난 순간 적용.
- 피트 손실은 단계별로 측정해 로그에 남긴다(진입 감속, 레인, 정차, 대기, 출구, 합류 교통).

## 12. 사건·로그·시간 손실 (log.js)

- 사건: `{t, lap, car(s), type, cause, effect}`.
- 시간 손실 계정(차량별, 랩별): 엔진이 아는 기준을 써서 **측정 가능한 것만** 분리.
  - 교통: 앞차 때문에 속도 제한을 받은 동안 `∫(1/v − 1/v_free)ds`(v_free = 같은 걸음의 자유 주행 한계 속도).
  - 피트: 단계별 시간 − 같은 거리 본선 자유 주행 시간.
  - 타이어·에너지·페이스 모드: **v0.48에서는 분리하지 않음**(깨끗한 반사실 기준이 없어 숫자로 내지 않고, 결과 화면에
    그렇게 밝힘 – 스틴트와 사건 기록으로 본다). 교통 손실은 traffic.js의 고스트(같은 타이어·에너지 모델, 교통 없음)로 근사.
  - 페널티: 규칙 시간.
  - 분리할 수 없는 나머지는 "기타"로 둔다(임의 분해 금지).

## 13. 3D 연결 (src/renderer/game/adapter3d.js, map3d.js의 게임 모드)

- 엔진 → 화면: 걸음마다가 아니라 렌더 프레임마다 **스냅샷**(차량: s, d, v, hdg, steer, 바퀴 회전각(거리 기반),
  타이어 컴파운드·마모, 에너지(게임 값 표시), 날개 상태, 피트 단계·작업 진행, 상태(달림/정지/리타이어); 세션: 날씨
  진실 현재값, 플래그, 시각). 화면은 두 스냅샷 사이를 보간(경기 계산에 영향 없음).
- map3d에는 `Map3D.game.attach(adapter)` / `detach()`로 들어가는 **명시적 게임 모드**를 둔다. 게임 모드에서 차량은
  어댑터 스냅샷으로만 배치되고(라이브 평활·겹침 보정·실측 그리드·마샬 RCM·실제 텔레메트리 경로는 꺼짐),
  같은 차량 모델·카메라·피트크루(엔진 작업 단계로 구동)·날씨 표현을 쓴다. 가짜 텔레메트리 객체를 만들지 않는다.
- 서킷: 게임 시나리오의 원본 랩 형상(같은 세션 위치 자료)으로 라이브와 같은 `buildWorld`를 쓰고, 엔진 `s` → 월드
  `s` 변환은 출발선 기준 비율(두 랩 라인 길이 차 보정).
- 게임 종료(`detach`) 후 라이브 모드는 원래대로(회귀 테스트·실제 화면).

### 13.1 스냅샷 계약 (엔진 → 화면)

`snapshot(race)`는 렌더 프레임마다 호출해도 되는 가벼운 순수 객체를 돌려준다(엔진 상태를 바꾸지 않음).

```js
{ t, scenarioId, totalLaps, leaderLap, flag: "grid"|"green"|"yellow"|"vsc"|"sc"|"red"|"chequered",
  sc: { s, d, v } | null,                     // 세이프티카 개체(트랙 위)
  weather: { rain, airT, trackT, wind, water, est },   // 진실의 현재값(화면 = 엔진), water: 평균 수막 mm
  cars: [{ num, teamKey, team, tla, color, status: "grid"|"run"|"pit"|"fin"|"dnf", pos, lap,
           where: "lap"|"pit", s, u, d, v, a, steer,          // s: 랩 m(where lap), u: 피트 경로 m(where pit), d: 횡 m(+왼쪽)
           wheelDist,                                        // 누적 주행 m(바퀴 회전 = 거리/반지름)
           aero: { open, front }, drs, overtake,             // 게임 상태(실제 텔레메트리 아님)
           tyre: { compound, wear, Ts, Tc, age }, energy: { soc, mode, deployKw }, fuel,
           pit: { phase, u, workT0, workT1, err, compound },     // compound: 이 정차에서 끼울 타이어(작업 중 크루가 들고 있는 것)
           gap: { leader, ahead } }] }                       // 초(랩 다운이면 leader는 null, lapsDown 별도)
```
`steer`: 앞바퀴 조향각(rad), +는 왼쪽. 추가 API: `events(race, sinceT)` → 그 이후 사건(로그·자동 감속용),
`results(race)` → 분류 + 차량별 시간 손실 계정(§12).
화면은 마지막 두 스냅샷(t₀ < t₁)을 렌더 시각으로 보간한다(s는 감쌈 보간, 피트 단계·상태는 t₁ 값). 보간은 엔진에
아무것도 쓰지 않는다.

## 14. 저장 (save.js)

`{engineVersion, scenarioId+hash, rulesVersion, paramsVersion, t, step, rng: {스트림 상태}, cars: [전체 상태],
pit: {박스·대기}, weather: {진실 커서, 수분 격자, 예보 상태}, control: {플래그, SC 개체}, incidents, ai: {팀별 상태},
commands: [접수된 명령 전체], pendingTransitions}`. 복원 → 같은 걸음에서 이어 실행 → 끝까지 결과 동일(테스트).

## 15. 데이터 경계와 API (data/, tools/)

- **원자료**(다운로드·캐시: 읽기 전용) → **시나리오**(`userData/game/scenarios/<id>.json`: 트랙·참가자·출발 순위·랩 수·
  날씨 기록, 출처·취득 시각·시즌·추정 표시) → **성능 자료**(`src/game/data/params`: 보정 결과, 보정/검증 경기 목록과
  오차) → **게임 상태**(엔진 메모리·저장 파일).
- 네트워크는 시나리오 준비 단계에서만(엔진 루프 밖). 준비된 시나리오는 오프라인 실행. API 실패 시 이전 시나리오/
  캐시로, 경기 중에는 네트워크를 쓰지 않음.
- 사용 가능 API와 조건은 `docs/game/research/apis.md`(조사 결과, 확인일).
